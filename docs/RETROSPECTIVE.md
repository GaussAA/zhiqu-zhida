# 知企智答 · 技术复盘

> 一个面向「介绍中国互联网公司」场景的 RAG 智能客服 Agent。本文不是使用手册，而是**为什么这样设计**——把关键决策、踩过的坑、以及量化验证讲清楚，便于评审与复用。

---

## 0. 一句话定位

用 **deepagents 编排 + FastAPI + React 19 三页工作台**，把「企业知识库问答」做成一个能跑、能测、能讲清决策的作品集级系统。约束条件是：**零 API 成本、可离线、密钥不入库、评估可量化**。

---

## 1. 架构一览（五层）

```
表现层  web/src (React 19 + Vite 7 + Tailwind v4)        三页：对话 / 知识库 / 日志
服务层  api.py + service.py (FastAPI)                   路由 / 内存多轮上下文 / 指标 / 导出
编排层  agent.py + intent.py (deepagents)               意图分类 + RAG 工具调用 + 客观命中判定
检索层  vectorstore.py (Chromadb + bge-zh 本地嵌入)      cosine 检索 + 距离阈值命中判定
数据层  db.py (SQLite) + Chroma                          companies + chat_logs + 向量库
```

完整职责表、数据流图、数据契约见 [`architecture.md`](./architecture.md)。本文只聚焦**有争议或反直觉的决策点**。

## 2. 四大关键决策与踩坑

### 2.1 客观命中判定：不信任模型自述

**决策**：`hit` / `fallback` 不由模型说「我检索到了」决定，而是由向量检索的 cosine 距离与阈值 `RETRIEVAL_MAX_DISTANCE=0.45` 客观计算。

**为什么**：LLM 在 RAG 里会「幻觉式自信」——即使 NO_HIT 也可能编出似是而非的引用。如果命中率统计依赖模型自述，指标就失去了审计价值。用距离阈值后：

- 日志里的命中率 / 兜底率真实可信；
- 前端徽章、日志标签、评估口径完全一致；
- 兜底触发条件统一，无歧义。

**代价**：阈值是一道硬边界，短事实问句可能卡在 0.45 附近抖动（见 2.3）。我们用「混合检索」而非「调高阈值」来解决，避免阈值放宽带来库外误召回。

### 2.2 模型免费优先 + 失败回退：成本零风险

**决策**：`MODEL_CANDIDATES = ["sensenova-6.7-flash-lite", "deepseek-v4-flash"]`，每次调用按序尝试，任一失败（超时 / 5xx / 空回答）即回退下一个；全部失败退回固定兜底话术。密钥仅走 `.env` 的 `SENSENOVA_API_KEY`，零硬编码。

**为什么**：作品集 / 演示场景下，API 账单是不可接受的隐性成本。免费额度密钥（sensenova）泄露面极小（最坏仅他人耗我每日免费额度），可放心用于演示；真付费密钥则严格走本地 `.env`，不入库、不进 CI。

**回退顺序的工程意义**：把「能跑」放在「跑得好」之前——宁可降级也要给出回答，绝不让用户看到裸异常栈。

### 2.3 混合检索：治「LLM 改写 query 削弱召回」（评估 87.5% → 100%）

**这是本项目最值得讲的一个坑。**

**现象**：评估报告首跑 87.5%，两条失败里最迷惑的是 `百度推出了哪款大模型？`——离线用 `vectorstore.search("百度推出了哪款大模型？")` 能命中（dist=0.4423 ≤ 0.45），但通过 `/api/chat` 真实问答却返回 NO_HIT。

**证伪过程**：在检索工具里临时加了 `RETROOL` 日志，打出 agent 真正传给工具的 query 与距离：

```
RETROOL q='百度 大模型' top=[(0.5298, '百度', False), ...]
```

真相大白——**deepagents 的 LLM 把用户问题自由改写为「百度 大模型」**（丢掉了「推出了哪款」），而这一短串与知识块的距离反而 0.5298 > 0.45，于是漏召。这是 RAG 的经典反模式：**为了让 query 更「检索友好」，LLM 的改写反而削弱了短事实问句的语义匹配**。

**解法（非降阈值、非改测试）**：检索工具**同时**用两路 query 检索并合并去重——

- 「agent 改写后的 query」（保留多轮指代消解能力，例如把「它」解析成「腾讯」）；
- 「用户原始问句」（保留短事实问句的忠实语义）。

合并后按距离排序取 top_k，再统一以 0.45 阈值判定。这样**两个能力都不丢**。

**效果**：重新评估 → **综合准确率 100.0%**（意图 / 来源 / 命中 / 兜底四项子指标全 100%），且多轮指代、闲聊、库外兜底均无回归。

> 另一处失败 `茅台股价现在多少？` 经核查是**评测期望写错**而非系统缺陷：茅台是真实公司、问「股价」属财务类，按本系统意图定义本就归「企业咨询」，仅因不在知识库内走兜底。校正评测标注即可，不动系统逻辑。

### 2.4 端口占用致索引未更新：37.5% 的「假象」（避坑指南坑 1）

**现象**：扩充种子到 10 家企业后首跑评估仅 37.5%，新增 6 家全部 MISS，但 `/api/companies/stats` 显示 `total=10`。

**根因**：在 Windows + git-bash 环境下，`pkill -f "uvicorn zhiqu.api"` **杀不掉 Windows 原生的 python 进程**。旧 uvicorn 仍占着 8720 端口，新进程绑定失败、启动即退出，**根本没执行 `rebuild_index()`**——对外服务的还是只含旧 4 家企业的残留 Chroma。

**解法**：用 `netstat -ano` 定位占用 PID，再用 `taskkill /F /PID`（注意 msys 路径转换会误伤 `/F`，加 `MSYS_NO_PATHCONV=1`）强杀，干净重启后核查 `collection.count()` 与块分布，再重跑评估。

**沉淀**：任何「改了种子 / 索引代码 → 重启 → 检索没变」的情形，第一反应是**端口被旧进程占用**，而非怀疑索引逻辑或盲目删库。详见 [`error_ledger.md`](./docs/error_ledger.md)（实际路径 `.workbuddy/memory/docs/error_ledger.md`）。

## 3. 评估体系：让「好不好」可量化

不是「跑通就算赢」，而是有断言、有指标、有报告：

- **16 条样例**：10 单轮跨企业命中 + 2 多轮指代 + 2 闲聊 + 2 库外兜底；
- **5 项指标**：意图准确率、来源归因准确率、命中正确率、兜底正确率、综合准确率（均 100%），外加平均耗时（~8.2s）；
- **产物**：`scripts/evaluate.py` 输出 `data/reports/eval_report_*.html`（指标卡 + 分布图 + 明细表），可截图、可分享；
- **回归护栏**：`e2e_m6.py`（综合 12 断言）+ `e2e_edge_m6.py`（边界 7 断言）覆盖增删重建、审核中不入检索、多轮堆叠指代、入参校验等。

## 4. 工程实践

- **原子化提交**：单个 commit 只含一个独立功能 / 修复 / 文档，Conventional Commits + 中文简述，便于评审与 bisect。
- **密钥零信任**：所有 Key 仅经环境变量读取，`.env` 已加入 `.gitignore`；仓库核验无任何真实密钥 / 运行时数据（`.workbuddy/`、`node_modules/`、`data/`、`web/dist/`）泄漏。
- **本地优先**：embedding 模型 `bge-small-zh-v1.5` 落在 `data/models/`，离线可用，不依赖外网下载。

## 5. 取舍与反思

| 没做 | 为什么暂不做 | 何时该做 |
|------|--------------|----------|
| 真后端在线托管 | 需常驻服务 + 暴露 API Key，与「零成本 / 零密钥泄漏」约束冲突 | 需要真实可聊 Demo 时，用 Docker + 环境变量注入部署 |
| 重排序（rerank） | 当前 10 家企业、短知识块，阈值 + 混合检索已够用 | 企业数上到百级、块变长时 |
| 流式输出 | 当前同步答已满足演示，成本 / 复杂度权衡后置 | 追求「类 ChatGPT」体验时上 SSE |

**核心方法论**：RAG 系统的「准不准」不能靠感觉，要靠**客观阈值 + 量化评估 + 逐条诊断日志**三者闭环。每一个「为什么没命中」，都应该能用一条检索距离数据回答，而不是靠猜。

## 6. 本地运行

```bash
# 后端（加载 bge 模型约 30–40s，自动 seed + rebuild_index）
uv run uvicorn zhiqu.api:app --app-dir src --port 8720

# 前端（另开终端）
cd web && pnpm install && pnpm dev        # 开发：5173 + 8720
# 或生产：pnpm build 后由后端单端口托管 dist

# 一键前后端（开发模式）
bash scripts/start.sh

# 跑评估（需后端在跑）
uv run python scripts/evaluate.py
```
