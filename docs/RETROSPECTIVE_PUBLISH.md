## 写在前面

做这个项目的动机很朴素：找 Agent / 架构师方向的岗位，作品集不能只放一个 "Hello World" 的 Demo。评审想看的不是"你跑通了一个系统"，而是——**你为什么这么设计，遇到坑怎么定位，怎么证明它真的好用**。

于是我给自己设了四条硬约束：

- **零 API 成本**：不能因为演示跑出一张账单；
- **可离线**：embedding 本地化，不依赖外网下载；
- **密钥不入库**：任何真实 Key 绝不进 git；
- **可量化评估**："好不好"要用数字说话，不能靠感觉。

带着这四条约束，我用 `deepagents 编排 + FastAPI + React 19` 做了一个面向「介绍中国互联网公司」场景的 RAG 智能客服 Agent。下面把最值得讲的几个决策和坑摊开讲。

> 仓库地址：https://github.com/GaussAA/zhiqu-zhida
> 在线 Demo：https://43c9e64be89441b38bc2ef459579596b.app.codebuddy.work

## 一、架构：五层，各司其职

```
表现层   React 19 + Vite 7 + Tailwind v4        三页：对话 / 知识库 / 日志
服务层   FastAPI                                路由 / 内存多轮上下文 / 指标 / 导出
编排层   deepagents + 意图分类                  意图识别 + RAG 工具调用 + 客观命中判定
检索层   Chromadb + bge-zh 本地嵌入             cosine 检索 + 距离阈值命中判定
数据层   SQLite + Chroma                        企业表 + 对话日志 + 向量库
```

设计上每层只干一件事，便于单独测试和替换。完整职责表和数据流图见仓库 `docs/architecture.md`，本文聚焦**有争议或反直觉的决策点**。

## 二、四个最值得讲的决策与坑

### 1. 客观命中判定：不信任模型自述

很多 RAG 系统的「命中率」是 LLM 自己说"我检索到了"算数的。我偏不。

`hit` / `fallback` 由向量检索的 **cosine 距离与阈值** 客观决定：

```python
RETRIEVAL_MAX_DISTANCE = 0.45   # 距离 ≤ 0.45 才判命中
```

为什么？因为 LLM 在 RAG 里会"幻觉式自信"——即使检索返回的是 NO_HIT，它也可能编出似是而非的引用。如果命中率依赖模型自述，这个指标就失去了审计价值。用距离阈值之后：

- 日志里的命中率 / 兜底率真实可信；
- 前端徽章、日志标签、评估口径完全一致；
- 兜底触发条件统一，无歧义。

代价是阈值像一道硬边界，短事实问句可能卡在 0.45 附近抖动。这个债，在第三个坑里还。

---

### 2. 模型免费优先 + 失败回退：成本零风险

```python
MODEL_CANDIDATES = ["sensenova-6.7-flash-lite", "deepseek-v4-flash"]
```

每次调用按序尝试，任一失败（超时 / 5xx / 空回答）就回退下一个；全部失败退回固定兜底话术。密钥只走 `.env` 的 `SENSENOVA_API_KEY`，零硬编码。

这里的工程取舍很清楚：**把"能跑"放在"跑得好"之前**——宁可降级也要给出回答，绝不让用户看到裸异常栈。免费额度密钥泄露面极小（最坏只是别人耗掉我的每日免费额度），可以放心用于演示；真付费密钥则严格走本地 `.env`，不入库、不进 CI。

---

### 3. 混合检索：治「LLM 改写 query 削弱召回」（87.5% → 100%）

**这是整个项目里最值得讲的一个坑。**

评估脚本首跑，综合准确率只有 **87.5%**。两条失败里最迷惑的是这一条：

> 问：`百度推出了哪款大模型？`
> 期望：命中「百度」来源
> 实际：NO_HIT，触发兜底

我第一反应是种子文本没对齐。离线用 `vectorstore.search("百度推出了哪款大模型？")` 测了一下——**能命中，距离 0.4423 ≤ 0.45**。可一旦走 `/api/chat` 真实问答，就漏召了。检索层和 API 层结论矛盾，必有蹊跷。

于是我在检索工具里临时加了一行日志，打出 agent **真正传给工具的 query**：

```
RETROOL q='百度 大模型' top=[(0.5298, '百度', False), ...]
```

真相大白——**deepagents 的 LLM 把用户问题自由改写成了「百度 大模型」**（丢掉了"推出了哪款"），而这串短词和知识块的距离反而 0.5298 > 0.45，于是漏召。

这是 RAG 的经典反模式：**为了让 query 更"检索友好"，LLM 的改写反而削弱了短事实问句的语义匹配。**

解法我没有选"降阈值"（那会带来库外误召回），也没有改测试（那是掩耳盗铃），而是**混合检索**——工具同时用两路 query 检索并合并去重：

- 「agent 改写后的 query」：保留多轮指代消解能力（比如把"它"解析成"腾讯"）；
- 「用户原始问句」：保留短事实问句的忠实语义。

合并后按距离排序取 top_k，再统一以 0.45 阈值判定。**两个能力都不丢。**

![真实对话：多轮指代消解与命中来源引用](https://43c9e64be89441b38bc2ef459579596b.app.codebuddy.work/site/assets/chat2.png)

重新评估 → **综合准确率 100.0%**（意图 / 来源 / 命中 / 兜底四项子指标全 100%），且多轮指代、闲聊、库外兜底均无回归。

> 顺带一提，另一条失败 `茅台股价现在多少？` 经核查是**评测期望写错了**，不是系统缺陷：茅台是真实公司、问"股价"属财务类，按本系统意图定义本就归"企业咨询"，只是不在知识库内走兜底。校正评测标注即可，不动系统逻辑。

### 4. 端口占用致索引未更新：37.5% 的「假象」

扩充种子到 10 家企业后，评估一度只剩 **37.5%**，新增 6 家全部 MISS——但 `/api/companies/stats` 显示 `total=10`，数据明明写进去了。

根因很阴：Windows + git-bash 下，`pkill -f "uvicorn zhiqu.api"` **杀不掉 Windows 原生的 Python 进程**。旧 uvicorn 仍占着 8720 端口，新进程绑定失败、启动即退出，**根本没执行 `rebuild_index()`**——对外服务的还是只含旧 4 家企业的残留 Chroma。

解法是用 `netstat -ano` 定位占用 PID，再用 `taskkill /F /PID`（注意 msys 路径转换会误伤 `/F`，得加 `MSYS_NO_PATHCONV=1`）强杀，干净重启后核查 `collection.count()` 与块分布，再重跑评估。

这个坑后来被我沉淀进项目的 `error_ledger.md`，立了一条铁律：**任何"改了种子 / 索引 → 重启 → 检索没变"的情形，第一反应是端口被旧进程占用，而非怀疑索引逻辑或盲目删库。**

## 三、评估体系：让「好不好」可量化

不是"跑通就算赢"，而是有断言、有指标、有报告：

- **16 条样例**：10 单轮跨企业命中 + 2 多轮指代 + 2 闲聊 + 2 库外兜底；
- **5 项指标**：意图准确率、来源归因准确率、命中正确率、兜底正确率、综合准确率（均 100%），外加平均耗时（~8.2s）；
- **产物**：`scripts/evaluate.py` 输出 HTML 报告（指标卡 + 分布图 + 明细表），可截图、可分享；
- **回归护栏**：综合 12 断言 + 边界 7 断言，覆盖增删重建、审核中不入检索、多轮堆叠指代、入参校验等。

## 四、取舍与反思

| 没做 | 为什么暂不做 | 何时该做 |
|------|--------------|----------|
| 真后端在线托管 | 需常驻服务 + 暴露 API Key，与"零成本 / 零密钥泄漏"冲突 | 需要真实可聊 Demo 时，用 Docker + 环境变量注入部署 |
| 重排序（rerank） | 当前 10 家企业、短知识块，阈值 + 混合检索已够用 | 企业数上到百级、块变长时 |
| 流式输出 | 当前同步答已满足演示，成本 / 复杂度权衡后置 | 追求"类 ChatGPT"体验时上 SSE |

**一句话方法论**：RAG 系统的"准不准"不能靠感觉，要靠 **客观阈值 + 量化评估 + 逐条诊断日志** 三者闭环。每一个"为什么没命中"，都应该能用一条检索距离数据回答，而不是靠猜。
